### <a name="_b7urdng99y53"></a>**Название задачи: Проектирование сценария просмотра истории покупок** 
### <a name="_hjk0fkfyohdk"></a>**Автор: Владимир Рябцев**
### <a name="_uanumrh8zrui"></a>**Дата: 24.02.2026**
### <a name="_3bfxc9a45514"></a>**Функциональные требования**
При реализации просмотра истории заказов должны быть учтены следующие функциональные требования:

|**№**|**Use Case**|**Описание**|
| :-: | :- | :- |
|F1|Просмотр списка заказов|В списке отображаются все заказы: сколько они стоили, когда были сделаны и каким способом доставлены.|
|F2|Просмотр деталей заказа|Для каждого заказа доступна подробная информация: список товаров, их количество и цена, итоговая сумма, способ доставки и оплаты, финальный статус заказа (доставлен, отменён).|
|F3|Другие действия с заказом|Покупатель может скачать чек, оставить отзыв о товаре или заказать его снова.|
### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
Выбранные архитектурные решения должны соответствовать предъявляемым нефункциональным требованиям:

|**№**|**Требование**|
| :-: | :- |
|P1|Отклик должен быть минимальным и не превышать одной секунды в 99,99%|
|P2|Ожидаемый показатель отлика в 98% равен 0,3 секунды|
### <a name="_qmphm5d6rvi3"></a>**Решение**
В рамках созданной архитектуры, каждый из микросервисов, участвующих в операциях по заказу (сервис платежей, сервис доставки), публикует в Kafka Topic события об изменениях, связанных с заказом, используя Transaction Outbox для гарантии доставки.

Под историю заказов было принято выделить отдельный микросервис, который агрегирует данные по заказу из событий в топике заказа (сохраняет/обновляет нужные поля в зависимости от события и его данных), записывает в оптимизированную для чтения модель БД и предоставляет REST API для пользователей мобильного приложения. 

В качестве базы данных была выбрана NoSQL документоориентированнная база данных MongoDB, позволяющая не использовать дополнительные преобразования (такие как JOIN в реляционных БД) для формирования ответа в формате JSON в REST API.

Благодаря использованию Kafka и Transaction Outbox, гарантируется согласованность read-модели в конечном итоге. Выбранное решение также позволяет масштабировать сервис истории заказов независимо от других сервисов системы.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
#### Альтернатива 1
В качестве дополнения к CQRS можно было бы использовать Event Sourcing, однако, его реализация накладывает дополнительные расходы на разработку и ресурсы системы. Поскольку в требованиях не указано, что нужно хранить всю историю изменений по каждому заказу, а необходимо только хранить текущее состояние заказа (текущий статус, итоговая стоимость, способ доставки, товары и прочее). Кроме того, отсутствуют требования к аудиту, что делает Event Sourcing избыточным решением и хватает обычного Event Log'а Kafka.

#### Альтернатива 2
API Composition может рассматриваться в качестве альтернативы CQRS, однако у него есть значенительные недостатки, препятствующие масштабированию и удовлетворению НФТ:

Каждая операция чтения требует обращения к нескольким микросервисам для сбора информации. Это значит, что страдает отказоустойчивость (если один из сервисов упал, часть информации будет получить невозможно) и скорость выполнения запроса (что является следствием использованием бОльшего числа ресурсов и сетевых запросов).

Даже если заняться кэшированием, возникнет проблема, связанная с инвалидацией кэша, которая будет происходить довольно часто, поэтому такой вариант тоже не подходит.
